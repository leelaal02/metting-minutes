# 회의를 듣고 회사 양식에 채워 넣는 파이프라인

녹음 파일이나 회의 메모를 넣으면 10개 항목으로 구조화되고, 사용자가 검토한 뒤
**자기 회사 회의록 양식(.docx)에 그대로 채워진 문서**가 나옵니다.
양식마다 다른 표 구조를 스스로 읽고 어느 칸에 무엇을 넣을지 판단합니다.

> 보기 좋은 버전: [`index.html`](./index.html) — 브라우저로 열면 됩니다 (로그인·인터넷 불필요).
> 파이프라인이 실제로 만든 파일: [`samples/`](./samples) — 빈 양식(`05`)과 채워진 결과(`08`)를 나란히 보세요.

## 1. 성과 — 양식이 바뀌어도 코드는 그대로입니다

표가 11행 2열인 양식, 표를 5개로 쪼갠 양식, **표가 아예 없는 문단형 양식**까지
**구조가 서로 다른 5종**을 같은 코드로 채웠습니다.
새 양식을 붙일 때 고친 코드는 없습니다 — 매핑만 새로 판단합니다.

| 지표 | 값 |
|---|---|
| 새 양식이 와도 고치는 코드 | **0줄** — 배치 판단만 새로 함 |
| 처리한 양식 | **5종** — 회사 양식 3종 · 자체 검증 양식 2종, 구조가 전혀 다름 |
| 양식이 달라도 바뀌지 않는 스키마 | **10항목 고정** |
| 가장 긴 원문 | **44,481자 → 6,039자** 회의록 (약 1/7 압축) |
| 그 회의록의 렌더링 실측 | **0.76초** (Markdown + docx) |
| 테스트 | **186개 전부 통과** (9.64초) · 코드 2,191줄 : 테스트 2,355줄 |

### "구조가 다르다"는 게 어느 정도인지

| 양식 | 구분 | 표 개수 | 구조 |
|---|---|---|---|
| A사 | 회사 | 1개 | 11행 × 2열 — 라벨/값 세로 나열 |
| B사 | 회사 | 2개 | 8행 × 4열 + Action Item 전용 18행 × 5열 |
| C사 | 회사 | 1개 | **표 1행 × 1열 + 문단 83개** — 사실상 표가 없는 문단형 |
| 자체 1 | 검증 | **5개** | 항목마다 표가 쪼개짐 (2×6, 1×2, 2×3, 2×3, 1×2) |
| 자체 2 | 검증 | 1개 | 10행 × 4열 — 주간 업무 회의 서식 |

회사 양식은 출처를 밝히지 않기 위해 A · B · C로 표기했습니다.
표 개수·행·열은 실제 산출물 `.docx`를 python-docx로 읽어 센 값이고,
나머지 수치도 저장소의 실제 산출물과 `pytest -q` 실행 결과에서 나왔습니다. 추정치는 넣지 않았습니다.

## 2. 병목은 요약이 아니라 *그다음*이었습니다

요약해 주는 도구는 이미 많습니다. 실무에서 막히는 곳은 요약 다음 —
결과를 다시 회사 양식 표에 하나씩 옮겨 붙이는 구간입니다.

| 기존 — 손으로 | 지금 — 명령 한 번 |
|---|---|
| 1. 녹음을 다시 들으며 받아적기 | 1. `/meeting-minutes` 호출, 녹음 파일 지정 |
| 2. 결정 / 미결 가려내기 | 2. STT → 10항목 추출 → **Markdown 미리보기** 자동 |
| 3. 서술식을 개조식으로 다듬기 | 3. 사람은 **미리보기를 읽고 고칠 것만** 말함 |
| 4. 회사 양식 워드 파일 열기 | 4. 양식 지정 → 표 구조를 읽고 배치 판단 |
| 5. 표 칸 찾아 **항목마다 복사·붙여넣기** | 5. 승인하면 완성된 `.docx` 출력 |
| 6. 담당·기한 빈칸 확인 요청 | |
| 7. 다른 부서 양식이면 **4–6단계 반복** | |

사람이 하는 판단은 **3단계 검토 하나**로 줄었습니다. 양식이 몇 개든 4–5단계만 다시 돌면 됩니다.

> 사람의 검토 단계는 없애지 않고 **일부러 남겼습니다.** 회의록은 틀리면 안 되는 문서라,
> 자동화의 목표를 "사람 없이"가 아니라 **"사람이 확인만 하면 되게"** 로 잡았습니다.

## 3. 결과물 — 빈 양식이 이렇게 채워집니다

실제로 처리한 **A사 회의록 양식**의 구조입니다.

**받은 양식** (표시자 없는 평범한 워드 표)

```
┌──────────────────────────────────────────┐
│                회 의 록                  │
├──────────────────────────────────────────┤
│ 제 목 :                                  │   ← 라벨이 두 번 나옴
├────────────────────┬─────────────────────┤
│ 일 시 :            │ 참 가 자            │
│ 장 소 :            │ 소 속 : 성명/직급 : │   ← 녹음에 없는 정보
├────────────────────┴─────────────────────┤
│ 제 목 :                                  │   ← 두 번째
├──────────────────────────────────────────┤
│ 회 의 내 용        (라벨 행)             │
│                    (빈 행 ← 진짜 값 자리)│
│ 향 후 일정 및 계획 (라벨 행)             │
│                    (빈 행)               │
│ 비 고              (라벨 행)             │
│                    (빈 행)               │
└──────────────────────────────────────────┘
```

**채운 결과** (사람 손 안 댐)

- `제 목 :` → 회의 제목
- `제 목 :` (두 번째) → 같은 값을 복사하지 않고 **회의 목적**
- `장 소 :` → 녹음에 없으므로 지어내지 않고 빨간 **입력필요**
- `회 의 내 용` 아래 빈 행 → `[논의 내용]` `[결정 사항]` `[미결 사항]` 3개 블록
- `향 후 일정 및 계획` 아래 빈 행 → `[실행 항목]`(담당/기한 포함) `[다음 회의]`
- `비 고` 아래 빈 행 → 기타·특이사항 (라벨이 위 행에 있으므로 섹션 제목 중복 안 붙임)
- 참석자 칸 → `총 3명 참석` 인원수 자동 계산
- 양식의 글꼴·자간·표 서식은 **그대로 유지**

## 4. 구조 — 판단은 LLM이, 변환은 코드가

설계의 중심에 이 경계선 하나를 뒀습니다. 사람의 판단이 필요한 일만 LLM에게 맡기고,
답이 정해진 일은 전부 코드로 고정했습니다. 경계가 흐려지지 않도록 단계 사이를
**명시적인 데이터 계약**으로만 연결했습니다.

```
[1] 입력      (코드) 텍스트 / 로컬 STT / 클라우드 STT — 어댑터 플러그인
      ↓ 계약: 정규화된 회의 원문 (UTF-8 문자열)
[2] 추출      (LLM)  회의 원문 → 10개 항목 구조화, 지시문(SKILL.md)이 규칙
      ↓ 계약: minutes.json — JSON Schema로 기계 검증되는 단일 진실 원천
[3] Markdown  (코드) 사람이 읽고 고칠 미리보기 — 승인 전에는 docx를 만들지 않음
      ↓ 계약: 사용자 승인
[4] docx      (코드) 양식 구조를 읽어 배치 → 검증된 표시자 삽입 → 값 채움
```

**계약이 하는 일**

- Markdown과 docx가 같은 스키마를 소비 → 두 산출물이 어긋날 수 없음
- 렌더러가 파일을 읽는 순간 자동 검증 → 규격 위반이면 잘못된 문서를 만드는 대신 **즉시 실패**
- 없는 값은 `null`만 허용 → **지어내기를 타입으로 차단**
- 출력 포맷을 늘려도 추출 단계는 그대로 재사용

**확장 지점**

```python
# scripts/adapters/__init__.py
REGISTRY = {
    "text":    text.transcribe,
    "whisper": whisper_local.transcribe,
    "groq":    groq_cloud.transcribe,
}
```

새 입력 방식 추가 = 모듈 1개 + 이 표에 한 줄.
실제로 v1은 텍스트만 지원하고 STT는 자리만 비워 뒀는데,
나중에 STT 2종을 붙일 때 **추출·생성·출력 계층은 한 줄도 고치지 않았습니다.**

## 5. 막혔던 지점과 푼 방법

### 5-1. 표시자가 없는 남의 양식을 어떻게 채우나 ★ 핵심 (848줄, 최대 모듈)

회사에서 받는 양식에는 `{{ title }}` 같은 치환 표시자가 없습니다. 그냥 평범한 워드 표입니다.
어디가 라벨이고 어디가 값 자리인지부터 알아내야 합니다.

**판단과 실행을 3단계로 쪼갰습니다.**

```
① inspect_template.py   양식 구조를 기계적으로 덤프 (의미 판단 없음)
        ↓ 구조 JSON
② LLM                   어느 항목을 어느 칸에 넣을지 결정
        ↓ 필드 이름만 담긴 매핑 (표시자 문법은 쓰지 않음)
③ apply_form_mapping.py 검증된 표시자만 삽입 → 문법 오류 원천 차단
```

**글자가 있냐 없냐만 봐서는 값 자리를 못 찾습니다.** 구조 덤프가 배치 신호 3가지를 함께 냅니다.

| 신호 | 무엇 | 없으면 생기는 사고 |
|---|---|---|
| `shaded` | 칸 배경색 유무 (색 무관) | 색칠된 **라벨 칸에 본문을 박아 넣음** |
| `numbered` | 문단의 자동 번호·글머리 유무 | 값을 적으라고 비워 둔 자리를 여백으로 오인 → `1.` `2.`만 남음 |
| `blocks` | 표와 문단이 놓인 **순서** | 표 끝이 라벨이면 진짜 값 자리(표 뒤 문단)를 놓침 |

**실제로 생성된 매핑** (앞의 A사 양식)

```jsonc
{"row": 1,  "col": 0, "mode": "inline", "fields": ["title"]},
{"row": 3,  "col": 0, "mode": "todo"},                        // 장소: 녹음에 없음 → "입력필요"
{"row": 4,  "col": 0, "mode": "inline", "fields": ["purpose"]}, // 두 번째 "제 목 :" 칸
{"row": 6,  "col": 0, "mode": "block",  "fields": ["discussion","decisions","open_issues"]},
{"row": 8,  "col": 0, "mode": "block",  "fields": ["action_items","next_meeting"]},
{"row": 10, "col": 0, "mode": "block",  "fields": ["notes"], "auto_label": false}
```

LLM이 쓰는 것은 **고정된 10개 항목 이름과 4가지 모드뿐**입니다. 표시자 문법은 코드가 만듭니다.
어휘를 벗어나면 실행 시점에 막히므로 **조용한 오배치 대신 명확한 실패**가 납니다.

**양식과 기호가 겹치는 문제** — 양식이 이미 `1.`을 쓰는 자리에 우리 소제목도 `1.`로 넣으면
두 계층이 구분되지 않습니다. 기호를 고정하지 않고 **그 자리에서 양식이 실제로 쓰는 기호를
읽어 비껴가는 사다리**를 만들었습니다.

```python
_TOPIC_LADDER = ["num", "□", "◇", "▪"]   # 소제목
_ITEM_LADDER  = ["-", "·", "‣", "◦"]     # 항목
```

이 밖에 예시 문구 자동 제거("내용을 작성하세요"·"OO팀 OOO"), 그 자리의 글꼴·크기 상속,
`총 __명 참석` 인원수 자동 계산, 표 행 나눔 금지 해제를 자동 처리합니다.

### 5-2. 에러 없이 조용히 빈칸으로 깨지는 버그

빈칸에 빨간 "입력필요"를 넣으려면 서식 있는 텍스트가 필요한데, docxtpl에는
**예외도 경고도 없이 그냥 빈칸으로 렌더되는** 함정이 있었습니다.
코드를 다 짠 뒤 발견했다면 구조를 되돌려야 했을 문제라,
**구현 전에 라이브러리를 직접 돌려 규칙 3가지를 확정하고 문서화**했습니다.

| 규칙 | 안 지키면 |
|---|---|
| 서식 텍스트는 `{{r ... }}`로만 넣는다 | run이 중첩된 잘못된 XML → **워드에서 빈칸** |
| 그 자리 값은 **값이 있어도** 항상 서식 객체로 감싼다 | 평문을 주면 **빈칸** |
| 컨텍스트 키를 **이원화**한다 (평문 키 유지 + `_rt` 신설) | 사용자가 쓰던 `{{ date }}` 양식이 **전부 깨짐** |

세 번째가 특히 하위 호환의 문제였습니다. 이미 표시자를 넣어 쓰던 양식을 깨뜨리지 않으려고
컨텍스트를 superset으로 설계해, 기존 키는 그대로 두고 서식 키를 추가로 실어 보냅니다.

함정이 하나 더 있었습니다. 서식 자리는 **렌더 시점에 런이 새로 만들어져** 앞 단계에서
입혀 둔 양식 글꼴이 사라집니다. 문단에 글꼴을 표식으로 남겨 두고
**저장 직전 후처리에서 글꼴 없는 런에만** 채워 넣도록 했습니다.

### 5-3. 데모는 되는데 실사용에서 터지는 것들

| 실제로 겪은 문제 | 해결 |
|---|---|
| 윈도우 콘솔이 cp949라 한글이 깨짐 | 표준 출력 버퍼에 UTF-8로 직접 씀 |
| 메모장 저장 설정 파일의 BOM 때문에 API 키 인식 실패 | `utf-8-sig`로 읽어 BOM 제거 |
| 1시간 넘는 녹음이 업로드 한도(25MB) 초과 | 번들 ffmpeg로 16kHz 모노 자동 재인코딩 (원본 불변) |
| 사용자가 경로 대신 파일 이름만 말함 | 작업 폴더 → 바탕화면 → 다운로드 → 문서 순 탐색 (깊이 제한) |
| 같은 날 비슷한 제목의 회의가 서로를 덮어씀 | 파일명에 `_2`, `_3` 자동 부여 |
| 같은 회의를 여러 양식에 채우면 파일명 충돌 | 양식명을 접두어로 (`A사_회의록_…`) |
| API 키 미설정 · 라이브러리 미설치 | 예외를 삼키지 않고 **원인과 해결 명령**을 담은 메시지로 변환 |

### 5-4. 요약이 "읽히는 회의록"이 되게 만들기

코드로 풀 수 없는 부분은 지시문 자체를 설계했습니다. 초기 결과물을 직접 읽어 보며
발견한 문제를 규칙으로 바꿔 못 박았습니다.

**결정과 미결을 절대 섞지 않는다** — 회의록에서 가장 먼저 찾는 구분인데 가장 자주 뭉개집니다.

```
결정 ✓ "지역별 단가 예측 제외, 전국 단가로 진행"
미결 ✓ "LLM 구축형 vs 상용 API 미정 (직접 구축 시 보안·버전 관리 부담)"
       └ 무엇이 걸려 있는지(쟁점·선택지)를 함께 적게 했습니다.
```

**개조식 강제 — 단, 정보는 줄이지 않는다**

```
서술식 ✗ "라마단이 지난 8월 18일에 끝났습니다. 따라서 중동 항로의 거래량이
         다시 늘어날 것으로 보입니다."
개조식 ✓ "라마단 종료 후 중동항로 물동량 회복 예상 (8/18)"
```

처음에는 "짧게 써라"로만 지시했더니 **정보가 함께 사라졌습니다.**
**"문장을 줄이는 것이지 사실을 줄이는 게 아니다"** 를 명시하고 좋은 예·나쁜 예를 함께 준 뒤 해결됐습니다.

## 6. 이 프로젝트로 보여드릴 수 있는 것

## 7. 회고

**잘한 결정**

- **계약을 스키마로 못 박은 것** — LLM 출력이 흔들려도 잘못된 문서가 나가지 않습니다.
- **미리 만들지 않은 것** — v1에서 STT는 자리만 비워 뒀습니다. 추상화를 미리 짓지 않고 **경계만** 그은 게 맞았습니다.
- **구현 전 실측** — 되돌리기 비싼 문제를 가장 싼 시점에 발견했습니다.

**어려웠던 점**

- 양식 매핑은 **정답이 하나가 아닌** 문제입니다. 규칙을 코드에 다 넣으면 양식마다 예외가 터지고,
  LLM에 다 맡기면 문법이 깨집니다. **판단은 LLM, 문법은 코드**로 나눈 뒤에야 안정됐습니다.
- 문체 규칙은 "짧게"만으로는 정보가 사라진다는 걸 결과물을 읽고 나서야 알았습니다.

**다음에 붙일 것**

- HWP 양식 직접 지원 (지금은 사용자가 .docx로 변환해야 함)
- 화자 분리로 발언자별 정리
- 출력 계층도 어댑터화 — 지금 확장 지점은 입력 쪽에만 있음
