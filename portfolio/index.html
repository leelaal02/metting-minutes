양식이 바뀌어도 코드는 그대로입니다

표가 11행 2열인 양식, 표를 5개로 쪼갠 양식, 표가 아예 없는 문단형 양식까지 구조가 서로 다른 5종을 같은 코드로 채웠습니다. 새 양식을 붙일 때 고친 코드는 없습니다 — 매핑만 새로 판단합니다.

"구조가 다르다"는 게 어느 정도인지

아래는 실제로 채운 양식 5종의 표 구조입니다. 라벨 이름만 다른 수준이 아니라, 표의 개수와 열 수 자체가 다르고 표가 없는 것도 있습니다.

양식구분표 개수구조
A사회사1개11행 × 2열 — 라벨/값 세로 나열
B사회사2개8행 × 4열 + Action Item 전용 18행 × 5열
C사회사1개표 1행 × 1열 + 문단 83개 — 사실상 표가 없는 문단형
자체 1검증5개항목마다 표가 쪼개짐 (2×6, 1×2, 2×3, 2×3, 1×2)
자체 2검증1개10행 × 4열 — 주간 업무 회의 서식

회사 양식은 출처를 밝히지 않기 위해 A · B · C로 표기했습니다. 표 개수·행·열은 실제 산출물 .docx를 python-docx로 읽어 센 값이고, 나머지 수치도 저장소의 실제 산출물과 pytest -q 실행 결과에서 나왔습니다. 추정치나 예상치는 넣지 않았습니다.

02변 화

병목은 요약이 아니라 그다음이었습니다

요약해 주는 도구는 이미 많습니다. 그런데 실무에서 막히는 곳은 요약 다음입니다 — 결과를 다시 회사 양식 표에 하나씩 옮겨 붙이는 일. 이 프로젝트가 없앤 건 그 구간입니다.

기존 — 손으로

  1. 녹음을 처음부터 다시 들으며 받아적기
  2. 무엇이 결정이고 무엇이 미결인지 가려내기
  3. 서술식 문장을 개조식으로 다듬기
  4. 회사 양식 워드 파일 열기
  5. 표 칸을 찾아 항목마다 복사·붙여넣기
  6. 담당·기한 빈칸을 표시해 두고 관계자에게 확인
  7. 다른 부서 양식이면 4–6단계를 처음부터 반복

양식이 바뀌면 사람이 처음부터 다시 합니다.

지금 — 명령 한 번

  1. /meeting-minutes 호출, 녹음 파일 지정
  2. STT → 10항목 추출 → Markdown 미리보기 자동
  3. 사람은 미리보기를 읽고 고칠 것만 말함
  4. 양식 지정 → 표 구조를 읽고 배치를 판단
  5. 승인하면 완성된 .docx 출력

사람이 하는 판단은 3단계 검토 하나로 줄었습니다. 양식이 몇 개든 4–5단계만 다시 돌면 됩니다.

사람의 검토 단계를 없애지 않고 일부러 남겼습니다. 회의록은 틀리면 안 되는 문서라, 자동화의 목표를 "사람 없이"가 아니라 "사람이 확인만 하면 되게"로 잡았습니다.

04구 조

판단은 LLM이, 변환은 코드가

설계의 중심에 이 경계선 하나를 뒀습니다. 사람의 판단이 필요한 일만 LLM에게 맡기고, 답이 정해진 일은 전부 코드로 고정했습니다. 경계가 흐려지지 않도록 단계 사이를 명시적인 데이터 계약으로만 연결했습니다.

1

입력 코드

텍스트 · 로컬 STT(faster-whisper) · 클라우드 STT(Groq) — 어댑터 플러그인

계약  →  정규화된 회의 원문 (UTF-8 문자열)
2

추출 LLM

회의 원문을 읽고 10개 항목으로 구조화 — 지시문(SKILL.md)이 규칙

계약  →  minutes.json — JSON Schema로 기계 검증되는 단일 진실 원천
3

Markdown 생성 코드

사람이 읽고 고칠 미리보기 — 승인 전에는 docx를 만들지 않음

계약  →  사용자 승인
4

docx 출력 코드 LLM은 배치 판단만

양식 없으면 기본 서식 / 있으면 구조를 읽어 배치 → 검증된 표시자 삽입 → 값 채움

계약이 하는 일

  • Markdown과 docx가 같은 스키마를 소비 → 두 산출물이 어긋날 수 없음
  • 렌더러가 파일을 읽는 순간 자동 검증 → 규격 위반이면 잘못된 문서를 만드는 대신 즉시 실패
  • 없는 값은 null만 허용 → 지어내기를 타입으로 차단
  • 출력 포맷을 늘려도 추출 단계는 그대로 재사용

확장 지점

# scripts/adapters/__init__.py
REGISTRY = {
  "text":    text.transcribe,
  "whisper": whisper_local.transcribe,
  "groq":    groq_cloud.transcribe,
}

새 입력 방식 추가 = 모듈 1개 + 이 표에 한 줄. 실제로 v1은 텍스트 입력만 지원했고 STT는 자리만 비워 뒀는데, 나중에 STT 2종을 붙일 때 추출·생성·출력 계층은 한 줄도 고치지 않았습니다.

05난 제

막혔던 지점과 푼 방법

가장 어려웠던 세 가지입니다. 필요한 만큼만 펼쳐 보세요.

1. 표시자가 없는 남의 양식을 어떻게 채우나 이 프로젝트의 핵심. 코드 848줄로 가장 큰 모듈입니다.

회사에서 받는 양식에는 {{ title }} 같은 치환 표시자가 없습니다. 그냥 평범한 워드 표입니다. 어디가 라벨이고 어디가 값 자리인지부터 알아내야 합니다.

해결 — 판단과 실행을 3단계로 쪼갰습니다

① inspect_template.py  양식 구조를 기계적으로 덤프 (의미 판단 없음)
                          ↓ 구조 JSON
② LLM                  어느 항목을 어느 칸에 넣을지 결정
                          ↓ 필드 이름만 담긴 매핑 (표시자 문법은 쓰지 않음)
③ apply_form_mapping.py 검증된 표시자만 삽입 → 문법 오류 원천 차단

글자가 있냐 없냐만 봐서는 값 자리를 못 찾습니다

그래서 구조 덤프가 배치 신호 3가지를 함께 냅니다.

신호무엇없으면 생기는 사고
shaded칸 배경색 유무 (회색·파랑·테마색 무관) 색칠된 라벨 칸에 본문을 박아 넣음
numbered문단의 자동 번호·글머리 유무 값을 적으라고 비워 둔 자리를 여백으로 오인 → 결과물에 1. 2.만 남음
blocks표와 문단이 놓인 순서 표 끝이 라벨로 끝나는 양식에서 진짜 값 자리(표 뒤 문단)를 놓침

실제로 만들어진 매핑

// 앞에서 본 A사 양식에 대해 실제로 생성된 mapping.json
{"row": 1,  "col": 0, "mode": "inline", "fields": ["title"]},
{"row": 3,  "col": 0, "mode": "todo"},                    ← 장소: 녹음에 없음 → "입력필요"
{"row": 4,  "col": 0, "mode": "inline", "fields": ["purpose"]},   ← 두 번째 "제 목 :" 칸
{"row": 6,  "col": 0, "mode": "block",  "fields": ["discussion","decisions","open_issues"]},
{"row": 8,  "col": 0, "mode": "block",  "fields": ["action_items","next_meeting"]},
{"row": 10, "col": 0, "mode": "block",  "fields": ["notes"], "auto_label": false}

LLM이 쓰는 것은 고정된 10개 항목 이름과 4가지 모드뿐입니다. 표시자 문법은 코드가 만듭니다. 어휘를 벗어나면 실행 시점에 막히므로, 조용한 오배치 대신 명확한 실패가 납니다.

양식과 기호가 겹치는 문제

양식이 이미 1. 번호를 쓰는 자리에 우리 소제목도 1.로 넣으면 두 계층이 구분되지 않습니다. 그래서 기호를 고정하지 않고 그 자리에서 양식이 실제로 쓰는 기호를 읽어 비껴가는 사다리를 만들었습니다. 

_TOPIC_LADDER = ["num", "□", "◇", "▪"]   # 소제목
_ITEM_LADDER  = ["-", "·", "‣", "◦"]     # 항목

이 밖에 "내용을 작성하세요"·"OO팀 OOO" 같은 예시 문구 자동 제거, 그 자리의 글꼴·크기를 읽어 그대로 입히기, "총   명 참석" 빈칸에 인원수 자동 계산, 표 행 나눔 금지 해제(긴 내용이 페이지 경계에서 통째로 밀리는 문제)를 자동 처리합니다.

2. 에러 없이 조용히 빈칸으로 깨지는 버그 구현을 시작하기 전에 실측으로 규칙부터 확정했습니다.

빈칸에 빨간 입력필요를 넣으려면 서식 있는 텍스트가 필요한데, docxtpl에는 예외도 경고도 없이 그냥 빈칸으로 렌더되는 함정이 있었습니다. 코드를 다 짠 뒤에 발견했다면 구조를 되돌려야 했을 문제라, 구현 전에 라이브러리를 직접 돌려 규칙 3가지를 확정하고 문서화했습니다.

규칙안 지키면
서식 텍스트는 {{r ... }}로만 넣는다 run이 중첩된 잘못된 XML → 워드에서 빈칸
그 자리 값은 값이 있어도 항상 서식 객체로 감싼다 평문을 주면 빈칸
컨텍스트 키를 이원화한다 (평문 키 유지 + _rt 키 신설) 사용자가 직접 쓰던 {{ date }} 양식이 전부 깨짐

세 번째가 특히 하위 호환의 문제였습니다. 이미 표시자를 넣어 쓰던 사용자의 양식을 깨뜨리지 않으려고 컨텍스트를 superset으로 설계해, 기존 키는 그대로 두고 서식 키를 추가로 실어 보냅니다.

여기에 함정이 하나 더 있었습니다. 서식 자리는 렌더 시점에 런이 새로 만들어져 앞 단계에서 입혀 둔 양식 글꼴이 사라집니다. 그래서 문단에 글꼴을 표식으로 남겨 두고 저장 직전 후처리에서 글꼴 없는 런에만 채워 넣도록 했습니다.

3. 데모는 되는데 실사용에서 터지는 것들 실제로 쓰면서 하나씩 막은 목록입니다.
실제로 겪은 문제해결
윈도우 콘솔이 cp949라 한글이 깨짐 표준 출력 버퍼에 UTF-8로 직접 씀
메모장으로 저장한 설정 파일의 BOM 때문에 API 키 인식 실패 utf-8-sig로 읽어 BOM 제거
1시간 넘는 회의 녹음이 업로드 한도(25MB) 초과 번들 ffmpeg로 16kHz 모노 자동 재인코딩 (원본 불변, 임시 파일 정리 보장)
